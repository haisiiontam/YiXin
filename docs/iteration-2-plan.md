# 迭代 2 计划：从“能跑”到“值得展示”

日期：2026-10-28。输入：`弈信-交付包-20261028.zip`（SHA256 `42db2625…ccbc2f`），基线提交 `04edaa5`。
基线验证（本迭代开始前实测）：合约 11 组 + 协议 4 组，共 15/15 通过。

## 1. 现状诊断（读源码后的结论，不是主观印象）

| 维度 | 现状 | 问题 |
| --- | --- | --- |
| 玩法 | 只有“真人双人”和“固定 9 手脚本演示” | 单人无法体验完整对局；老师验收时没有对手 |
| 回看 | 只有当前棋盘 | 结算后无法复盘，FR-25（棋谱逐步回放，P1）尚未实现 |
| 信息密度 | 实验室只有交易条形图 | 棋局本身没有“局势”“威胁”等可视化 |
| 证据 | 只有 JSON | 非技术读者无法直观看懂“这局棋为什么可信” |
| 外观 | 浅绿灰卡片、单一无衬线字体、字号 7–11px 的大量细字 | 缺乏棋类产品应有的质感，小字在 1080p 下可读性差 |
| 代码结构 | `App.jsx` 120 行但单行极长；`styles.css` 8 行、33 KB | 难以维护，不利于课程强调的“可维护性 NFR-11” |

## 2. 方案取舍

候选功能按“工程价值 × 展示效果 × 风险”打分，只做前四项高分项以及配套的外观重做。

| 候选 | 工程价值 | 展示效果 | 风险 | 决定 |
| --- | --- | --- | --- | --- |
| A 人机对弈（AI 是第二个本地钱包，每手仍双签，终局链上结算） | 高：复用全部协议，证明协议可承载非真人对手 | 高 | 中：AI 强度与耗时 | 做 |
| B 复盘时间轴 + 形势曲线（实现 FR-25） | 高：补齐 P1 需求，纯函数可单测 | 高 | 低 | 做 |
| C 威胁识别 / 落子点评 / 提示 | 中：与 AI 共用分析器，零额外成本 | 高 | 低 | 做 |
| D 对局证书（SVG 导出，含棋谱缩略图、摘要、交易 hash） | 中：把“可验证”变成可展示物 | 高 | 低 | 做 |
| E 合成音效（WebAudio，无音频素材，规避版权） | 低 | 中 | 低 | 做（可关闭） |
| F 公网联机 / 排行榜 | 中 | 中 | 高：违反“不部署公网”规则，且有女巫攻击 | 不做，列入局限 |
| G 修改合约（加悔棋、计时） | 高 | 中 | 高：会使 11 组合约测试与报告数据失效 | 不做 |

关键约束：**不改合约与 `shared/gomoku.mjs` 的既有导出**，因此既有 11+4 组测试与报告数据继续有效；新增能力全部放在新增文件或客户端/前端层。

## 3. 新增需求（追加到需求追踪，编号接续 FR-26 / NFR-15）

| 编号 | 优先级 | 需求 | 验收标准 |
| --- | --- | --- | --- |
| FR-27 | P0 | 人机对弈：选择难度后与本地 AI 对局 | AC-F27：AI 钱包独立生成；每手人与 AI 均对完整棋谱做 EIP-712 签名；对局仍为 open+join+settle 共 3 笔链上交易；终局可链上结算并积分守恒 |
| FR-28 | P1 | 复盘：任意手数回看棋盘 | AC-F28：滑块/上一步/下一步/首尾跳转；回看不发交易、不改积分；回看第 k 手的棋盘等于 `evaluate(moves.slice(0,k))` |
| FR-29 | P1 | 形势曲线与落子点评 | AC-F29：曲线长度等于手数；开局为 0；连五后绝对值 ≥ 0.99；点评文字来自共享分析器 |
| FR-30 | P2 | 威胁与提示：标出必须封堵的点，可请求 3 个建议 | AC-F30：提示不发交易；终局后无提示；建议点均为空位 |
| FR-31 | P1 | 对局证书导出 | AC-F31：证书含通道 ID、双方地址、手数、状态摘要、交易 hash；不含私钥；篡改手数无法通过原证据校验 |
| NFR-16 | P1 | 视觉与可访问性 | 统一设计令牌；正文不小于 13px；日/夜两套主题；对比度正文 ≥ 4.5:1；`prefers-reduced-motion` 关闭动效；既有 E2E 可访问名称不变 |
| NFR-17 | P1 | 新模块可测试性 | 分析器与 AI 为无 DOM 纯函数，有独立单测与真实自博弈统计 |
